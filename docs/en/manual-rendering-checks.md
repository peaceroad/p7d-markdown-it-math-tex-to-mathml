# Manual Rendering Checks

This document describes how to run manual browser checks for the project's rendering fixtures.

Use it as a practical checklist, especially when checking native MathML behavior on iOS/WebKit.

## Fixture pages

The rendering fixture source is:

- `example/src/example-rendering-check.md`

Recommended generated pages:

- `example/generated/compare/example-rendering-check-compare.html`
- `example/generated/compare/example-rendering-check-mode-compare.html`

Other single-view pages live in `example/generated/pages/` and are mostly direct inspection pages or iframe sources for the compare views.

These pages are generated by:

- `example/build-examples.js`

If you edit the source fixture, regenerate the HTML with:

```sh
node example/build-examples.js
```

## Recommended check order

1. Run the normal automated tests.
2. If the fixture source changed, regenerate the example HTML pages.
3. Open the relevant rendering check pages in the target browser.
4. Compare MathML and SVG output for the same expressions.
5. When evaluating variant-sensitive output, also compare default MathML with `mathmlMode: 'mathjax'`.
6. If the issue appears on iOS Safari, compare normal page rendering with Reader mode.

## Verification Targets

### 1. Function-like identifiers followed by `(`

Primary regression target:

- `\text{MSA}(LN)`
- `\operatorname{MSA}(LN)`
- similar `\text{word}(` and `\operatorname{word}(` patterns

Check that:

- the opening parenthesis does not overlap the preceding letters
- inline and display math both behave acceptably

If SVG is correct while MathML is wrong, treat that first as a browser-native MathML rendering issue, not as a TeX parsing issue.

### 2. Variant rendering

Check representative variant samples:

- `\mathbb`
- `\mathbf`
- `\mathcal`
- `\mathfrak`

This is mainly a visual sanity check. The exact serialized-output contract is already covered by automated tests.
When comparing default MathML with `mathmlMode: 'mathjax'`, focus on whether explicit variant-origin glyph differences shrink enough to matter in practice.

### 3. Broad-package constructs

Check examples such as:

- `\cancel{x}`
- `\tag{1} x`

These are useful because they remind you that default output is broader than strict MathML Core.

### 4. Reader mode comparison on Safari

When a rendering problem appears on iOS Safari:

- compare normal page rendering with Reader mode

If Reader mode looks correct while the normal page does not, suspect page CSS / typography interaction before suspecting TeX parsing.

## Recording Rendering Bugs

Record at least:

- browser and version
- device/OS
- which fixture page was used
- whether the issue appears in MathML only, SVG only, or both
- whether Safari Reader mode changes the result

That makes later regressions easier to compare without turning this document into a tooling discussion.
